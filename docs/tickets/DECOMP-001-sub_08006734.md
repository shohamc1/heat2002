# DECOMP-001: `sub_08006734` — first function, prove the pipeline

**Status:** open
**Priority:** P0 (blocks every other ticket)
**Target:** `sub_08006734` @ `0x08006734`
**Size:** 1 instruction (`bx lr`), 2 bytes
**Callers:** 38 distinct — 8th highest in-degree of 743 functions
**Leaf:** yes (no `bl`)

## Why this one

Recon (`docs/recon.md`) ranked all 743 functions on size, leaf status, and
in-degree. This function is the outlier where "easiest possible" and "high
leverage" coincide:

| Candidate | Insns | Leaf | Callers | Note |
| --- | ---: | :---: | ---: | --- |
| **`sub_08006734`** | **1** | **yes** | **38** | recommended |
| `sub_08016558` | 6 | yes | 51 | most callers, but 6 insns of table math |
| `sub_08016E10` | 2 | yes | 24 | `swi #11` — needs inline asm |
| `sub_0800048C` | 16 | yes | 40 | straight-line but 16 insns |

Of the 21 other one-instruction functions in the ROM, none has more than 3
callers. This one has 38. It is a return-only stub, so there is almost no
codegen to get wrong — which makes it the lowest-risk end-to-end test of the
whole C → agbcc → assembler → linker → SHA1 chain.

The real goal of this ticket is **not** the 2 bytes. It is proving the
workflow works, including the part nobody has exercised yet: removing a
function from `asm/rom.s` and linking a C-compiled replacement in its exact
place without breaking the byte-for-byte match.

## Target asm

```asm
 thumb_func_start sub_08006734
sub_08006734:
 bx lr
 thumb_func_end sub_08006734
```

## Steps

1. Create `src/stub.c`. A function whose body compiles to a bare `bx lr` —
   returns nothing, does nothing:

   ```c
   void sub_08006734(void) {}
   ```

2. Build and compare:

   ```
   make
   python3 scripts/match.py sub_08006734
   ```

   Expect `MATCH (1 insns)`. If you get `pop {r0}; bx r0` instead of `bx lr`,
   the function is being treated as non-leaf — check that the body is truly
   empty.

3. Remove the function from `asm/rom.s` (the `thumb_func_start` through
   `thumb_func_end` block, inclusive).

4. Place the C version at the identical address. **This is the hard part and
   the real deliverable of the ticket.** `ldscript.ld` currently emits
   `build/asm/rom.o(.text*)` as one blob at `0x08000000`; a single removed
   function leaves a 2-byte hole that the linker will not fill on its own.
   Expect to either split `asm/rom.s` at the extraction boundary, or add an
   explicit `. = 0x08006734;` placement for the new object. Getting this
   right is what makes tickets 002+ mechanical.

5. Verify nothing moved:

   ```
   make check     # must print MATCH
   ```

6. Record progress and commit:

   ```
   python3 scripts/progress.py
   git add -A && git commit -m "Decompile sub_08006734"
   ```

## Done when

- [ ] `scripts/match.py sub_08006734` prints `MATCH`
- [ ] Function is gone from `asm/rom.s` and lives in `src/`
- [ ] `make check` prints `MATCH` (SHA1 `0eb1fa43…` unchanged)
- [ ] `scripts/progress.py` reports 1/743 functions
- [ ] Linker placement approach is written down in `CLAUDE.md` for reuse

## Risks

- **Placement, not codegen, is the blocker.** The C will almost certainly match
  on the first try; the ldscript surgery is where this ticket will actually be
  spent. If splitting `asm/rom.s` per-function turns out to be needed, that is
  a tooling change worth doing once, properly, here.
- A return-only stub may be a compiler-generated no-op rather than a real game
  function. It matches regardless, so this does not block the ticket — but do
  not read meaning into its name or purpose.
- `sub_08006734`'s true signature is unknown. `void(void)` is what matches the
  asm; the real function may take arguments that are simply ignored. Revisit
  when callers are decompiled and the actual call sites become readable.
